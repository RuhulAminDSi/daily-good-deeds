# Database Design

> Status: **Specification (Stage 4). Not implemented.** The target is PostgreSQL 16+ on Neon, accessed through Prisma (see [TECH_STACK_DECISION.md](../TECH_STACK_DECISION.md)).
> The binding table inventory is [docs/README.md §6](../README.md#6-canonical-table-inventory-validated-from-the-directives-entity-list). Related docs: [ERD.md](ERD.md) · [DATA_DICTIONARY.md](DATA_DICTIONARY.md) · [INDEXING_STRATEGY.md](INDEXING_STRATEGY.md) · [MIGRATION_STRATEGY.md](MIGRATION_STRATEGY.md)

## 1. Design principles

1. **Normalize first (3NF), then denormalize only for measured needs.** The only planned denormalizations are derived caches (`streaks`, `daily_summaries`, `growth_snapshots`) and the counters on `posts`. Each one can be rebuilt from source rows.
2. **The owner is explicit on every row.** Every user-owned row has a non-null `user_id` FK to `users`. Shared content uses either `owner_user_id IS NULL` (system content) or a group scope (`group_id`).
3. **Use UUIDv7 primary keys** (`uuid`, generated by the application). They are time-ordered, so B-tree locality stays good. They can also be generated offline by the PWA outbox and the widget, which makes sync idempotent (see §8).
4. **All instants are stored as `timestamptz` in UTC.** Calendar facts use `date` (`local_date`) together with the user's IANA timezone (see §5).
5. **The database enforces invariants:** FKs with explicit `ON DELETE` rules, `CHECK` constraints, partial unique indexes, and `NOT NULL` by default. Business rules that span rows stay in the domain layer (`packages/domain`), which is shared with the client.
6. **Private by default.** Data never leaves its owner unless a visibility column explicitly allows it. Journal bodies are encrypted at the application level (see §9).
7. **No hard dependence on AI or external content.** Tables for AI and cached external content can be empty without breaking any core flow.
8. **Naming:** `snake_case`, plural table names, `*_id` foreign keys, `is_*`/`has_*` booleans, `*_at` timestamps, and `*_on`/`local_date` for calendar dates.
9. **Standard columns:** `id uuid PK`, `created_at timestamptz NOT NULL DEFAULT now()`, and `updated_at timestamptz NOT NULL DEFAULT now()` (maintained by Prisma `@updatedAt`). Append-only logs omit `updated_at`.

## 2. Module ownership

Each NestJS module owns its tables. Other modules may **read** them only through the owning module's service layer, never by writing directly. Exception: the `sync` module dispatches each operation to the owning module's command handler.

The **single** module-to-tables map is in [architecture/COMPONENT_ARCHITECTURE.md](../architecture/COMPONENT_ARCHITECTURE.md), which also drives the `eslint-plugin-boundaries` config. It is not repeated here so it cannot drift.

pg-boss owns the separate `pgboss` schema, which Prisma does not manage (see [MIGRATION_STRATEGY.md](MIGRATION_STRATEGY.md) §2).

## 4. Multi-tenant isolation and visibility

- **User-scoped data** (completions, plans, journal, salah, goals, AI, notifications, …): every repository method takes the authenticated `userId` and adds `WHERE user_id = $userId`. A Prisma client extension (`scopedPrisma(userId)`) injects the filter on user-owned models. CI runs a lint rule that rejects raw `prisma.<userOwnedModel>` access outside repositories.
- **Defense in depth (Phase 10, optional):** Postgres Row-Level Security policies on the most sensitive tables (`journal_entries`, `salah_records`, `ai_messages`), keyed on `current_setting('app.user_id')`. RLS is enabled only after load testing confirms the overhead is acceptable (it is tracked as an ADR).
- **Group-scoped data:** a member can read group content only when there is a `group_members` row with `status = active` for that user. Personal data (completions, salah, journal) is **never** joined into group queries. Group challenges read only `challenge_progress`, which the participant writes explicitly (opt-in sharing per F-COMM-014).
- **Visibility enum** (`visibility`: `private`, `group`, `community`, `public_anonymous`) applies to `posts` only. Journal entries have no visibility column. They cannot be shared.
- **Blocks:** queries that return community content exclude authors where a `user_blocks` row exists in either direction.
- **Admin access:** admin endpoints read user data only through `/admin/*` services. These check permissions (`user.read` etc.) and write an `audit_logs` row on every read of personal data. Journal ciphertext is **never** decrypted for admins.

## 5. Time model: `local_date` + timezone

Streaks, checklists, and "today" all depend on the **user's** calendar day, not the UTC day.

- `user_preferences.timezone` stores an IANA name (for example `Asia/Dhaka`), validated against `Intl.supportedValuesOf('timeZone')`.
- Every per-day fact stores `local_date date NOT NULL`: the date in the user's timezone **at the moment of the action**, computed by the client and validated by the server. The row also stores `occurred_at timestamptz` (the true instant) and `tz text` (the timezone in effect).
- The server accepts a client `local_date` only if it falls within ±1 day of `occurred_at` converted to the stated `tz`. This covers travel and devices on the date line. Anything else is rejected with `LOCAL_DATE_OUT_OF_RANGE` (see [api/ERROR_HANDLING.md](../api/ERROR_HANDLING.md)).
- **Changing timezone does not rewrite history.** Past rows keep their `local_date`. Only future boundaries change. Streak computation runs over `local_date` sequences, so a trip from Dhaka to London neither breaks nor double-counts a day.
- Past-day edits are limited by the setting `completions.edit_window_days`. The rule is SRS FR-CAL-011-01; the key and default are in the [Settings registry](DATA_DICTIONARY.md#settings-registry). The limit is enforced in the service layer, not by a CHECK, because it is configurable.
- Reminders store `next_fire_at timestamptz` (UTC). It is computed from the local schedule and timezone when the reminder is written, and again after each fire. One indexed scan per minute (`WHERE enabled AND next_fire_at <= now()`) serves all reminders, including prayer reminders (DL-024). One-shot deliveries, such as future-self letters, are pg-boss jobs with `startAfter`.

## 6. Recurrence storage

`deed_plans` and `planner_items` (when recurring) store:

| Column | Example | Meaning |
|---|---|---|
| `rrule` | `FREQ=WEEKLY;BYDAY=MO,TH` | A **restricted RFC 5545 subset**: `FREQ` ∈ {DAILY, WEEKLY, MONTHLY}; `INTERVAL` 1–30; `BYDAY` (weekly only); `BYMONTHDAY` 1–31 or −1 (monthly only); `COUNT` or `UNTIL`. No `BYSETPOS`, `BYHOUR`, or `EXDATE`. Validated by `packages/domain/recurrence` on both client and server |
| `dtstart_local` | `2026-11-01` | The first occurrence as a local date. Recurrence is evaluated in the user's timezone on `local_date`s, so DST cannot shift days |
| `ends_on` | `2027-01-31` / NULL | A materialized end date (derived from `UNTIL`/`COUNT`) for indexing |
| `paused_from`, `paused_until` | | Pausing (for example during travel or illness) suspends occurrences without counting them as misses |

**Occurrences are not materialized.** The checklist for date D is the set of active plans whose rule matches D, left-joined with completions for D. Evaluating ≤ 200 plans per user in memory is cheap for a single day. Multi-day views (calendar, heatmap, year) read `daily_summaries` instead of re-evaluating rules for each day (§7). One-off deeds use `rrule = NULL` with `dtstart_local` as the single date.

## 7. Derived caches (rebuildable)

| Cache | Source of truth | Update | Rebuild |
|---|---|---|---|
| `daily_summaries` (user × local_date: scheduled, done, partial, skipped) | `deed_completions` + `deed_plans.rrule` | In the same transaction as the completion write. A plan edit updates rows from today forward | The `streaks.rebuild:{userId}` job recomputes it from completions |
| `streaks` (per user × plan, plus one overall row with `deed_plan_id NULL`) | `deed_completions` + `deed_plans.rrule` (the overall row uses `daily_summaries`) | Incrementally in the completion transaction, **only** for today/yesterday (extend or end the run) | One debounced `streaks.rebuild:{userId}` job. Past-day edits, plan-rule changes, timezone corrections and sync batches enqueue it. Idempotent (DL-023) |
| `growth_snapshots` (user × month) | completions, goals, journal counts (counts only, never content), life balance | Nightly job for the previous month, plus on-demand for the current month | Delete and recompute |
| `posts.reaction_count`, `posts.comment_count` | `reactions`, `comments` | Same-transaction increment | Recount job |

Streak rules: **[SRS §7.5.1](../specifications/SRS.md) is the only definition.** Its fixed thresholds are domain constants in `packages/domain` (DL-017). The edit window is the `completions.edit_window_days` setting.

## 8. Offline sync support

SRS §19 and [api/API_SPECIFICATION.md](../api/API_SPECIFICATION.md) own the protocol: endpoints, op statuses and the conflict rule. This section covers only the storage it needs.

- Clients generate UUIDv7 IDs offline. Every mutation in the outbox carries an `op_id` (UUID).
- `sync_operations (user_id, op_id)` is the primary key. A replayed op returns the stored result, so ops are idempotent. The server checks a whole batch with one `op_id = ANY($1)` query.
- **Syncable tables** carry two columns:
  - `change_seq bigint NOT NULL`, taken from one global sequence (`change_seq_global`) and set on every insert, update and soft delete.
  - `client_updated_at timestamptz`, used by the conflict rule.

  Conflicts are resolved **per row**: the latest client time wins, and the losing row is stored in `sync_operations.conflict` (DL-015).

  The syncable tables are `deed_plans`, `deed_completions`, `planner_items`, `salah_records`, `dhikr_logs`, `practice_logs`, `fasting_records`, `quran_reading_logs`, `goals`, `goal_milestones` and `wellbeing_logs`.

  **`journal_entries` is not syncable**, because journals are online-only (DL-021).
- `deed_completions` has a natural unique key `(user_id, deed_plan_id, local_date)`, so the same completion from web and widget collapses into one row (upsert).
- **Delta pull** runs `WHERE user_id = $1 AND change_seq > $cursor` on each syncable table, using an index on `(user_id, change_seq)`. The cursor is the highest `change_seq` returned. When nothing has changed, the pull costs one cheap index probe per table and the API can answer 304.
- **Deletions** use soft-delete tombstones (`deleted_at`) on syncable rows, so they reach other devices. SRS NFR-PRIVACY-009 sets how long tombstones are kept (§12).

## 9. Journal encryption

`journal_entries` stores free text encrypted at the application level with AES-256-GCM and a single versioned application key (DL-030):

| Column | Type | Purpose |
|---|---|---|
| `title_ciphertext` | bytea NULL | Encrypted title (optional) |
| `body_ciphertext` | bytea NOT NULL | Encrypted body (rich text as JSON or Markdown, UTF-8) |
| `nonce` | bytea NOT NULL (12 bytes) | GCM IV, unique per write |
| `key_version` | smallint NOT NULL | Which version of the application key (env/KMS) encrypted the row. Enables rotation |
| `tags` | text[] | **Plaintext**, user-chosen labels for filtering. The UI tells the user that tags are not encrypted |
| `mood` | smallint NULL | 1–5, plaintext, used in aggregates |

- The key comes from the environment or KMS and is never stored in the database. There are no per-user keys, because wrapped keys kept in the same database and backups would add no protection.
- **Key rotation:** new writes use the new key version. Old rows are re-encrypted lazily on their next write, or by a background job that bumps `key_version`. A retired key version stays available until no row references it.
- `future_letter` and `monthly_reflection` entries use the same scheme. Future-letter delivery decrypts in the worker only to send the letter to the owner.
- Search limitation: see [INDEXING_STRATEGY.md §4](INDEXING_STRATEGY.md#4-journal-search-and-encryption).
- The same pattern (ciphertext + nonce + key_version) applies to `ai_messages.content` (§13) and to the free-text notes on `wellbeing_logs.note_ciphertext`. `deed_completions.note` is **not** encrypted (short, lower sensitivity). This is recorded as an accepted risk and can be revisited.

## 10. Translation pattern

There are two patterns, chosen by content type:

| Pattern | Used for | Shape |
|---|---|---|
| **A. `*_translations` child table** | Admin-managed, searchable, versioned content: deeds, deed categories, achievements, duas, hadith | `(parent_id, locale)` unique; `locale` ∈ `('en','bn')` CHECK; text columns only. There is **no per-translation status or reviewer**: review state lives on the parent (DL-031). A missing BN row falls back to EN (F-I18N-009) |
| **B. `jsonb` label map** | Small, seed-defined lookups that are rarely edited: `life_balance_categories.name`, `sunnah_practices.name`, `dhikr_presets.meaning`, `affirmations.text`, `campaigns.title/description`, `roles.description`, `permissions.description` | `{"en": "...", "bn": "..."}` with `CHECK (name ? 'en')` |

User-generated content (custom deeds, posts, comments, goals) is **not translated**. It stores a `locale` column for rendering hints and moderation.

## 11. Content versioning

For admin-managed content (deeds, categories, achievements, duas, hadith, campaigns, sunnah practices, dhikr presets):

- Parent rows carry `status content_status` and `version int`. General content uses only `draft`, `published` and `archived`. `in_review`, `verified_by` and `verified_at` exist **only** on religious content (`duas`, `hadith_entries`, `dhikr_presets`) (DL-031).
- Every publish writes a `content_versions` row: `entity_type`, `entity_id`, `version`, `snapshot jsonb` (parent + all translations), `changed_by`, `change_note`. Rollback restores from the snapshot as a **new** version. History is never rewritten.
- Religious content (`duas`, `hadith_entries`, `dhikr_presets`) cannot go to `published` without `source_id` and `verified_by` + `verified_at` (CHECK constraints plus service rule, F-ISL-018 / F-ADMIN-005). The reviewer must differ from the author; this is enforced in the service.
- Users' completions reference `deeds.id`, not a version. Editing a deed's wording does not alter history. Archived deeds stay resolvable.

## 12. Lifecycle, retention, and deletion

Retention **periods** are defined only in SRS NFR-PRIVACY-009 (personal data, sync ledger, tombstones, AI content, notifications) and NFR-BACKUP-002 (backups). This section covers only the **mechanism**. Where a period can be tuned by an admin, its key is in the [Settings registry](DATA_DICTIONARY.md#settings-registry).

| Data | Mechanism |
|---|---|
| Account deletion (F-AUTH-009) | A request sets `users.deletion_requested_at`, revokes sessions and locks the account. The user can cancel by logging in and confirming. After the grace period in SRS FR-AUTH-009-01, the `account:purge` job hard-deletes the `users` row, and user-owned tables cascade (`ON DELETE CASCADE` from `users`). Each phase that adds user-owned tables or object-storage files extends this job and its test. |
| Community content on deletion | Posts and comments are **kept but de-identified**: `author_id` is set to NULL (`ON DELETE SET NULL`) and shown as "Former member". Users can delete individual posts before deleting their account. |
| Audit logs | Append-only. A nightly batched `DELETE … WHERE occurred_at < now() - retention` removes old rows (DL-027). On account purge, actor and subject UUIDs are kept, but that user's display and IP fields are **pseudonymized** (`ip` → NULL, display → `deleted-user:<hash>`). |
| Moderation records | Kept after resolution for the moderation-trail period, even after the reported user is deleted. Subject FKs are SET NULL and the evidence snapshot is kept. |
| Sessions, verification tokens, `idempotency_keys` | The daily `maintenance:purge` job removes expired rows. |
| `sync_operations`, tombstones (`deleted_at`) on syncable rows | `maintenance:purge` removes them after the period in NFR-PRIVACY-009. |
| `ai_messages` / `ai_conversations` | The user can delete them at any time. `maintenance:purge` deletes them automatically after the NFR-PRIVACY-009 period. `ai_usage_logs` holds no content. |
| `notifications` | `maintenance:purge` removes them, using a BRIN index on `created_at`. |
| `export_jobs` files | An object-storage lifecycle rule expires the files. The row is kept as status history. |
| Backups | Neon PITR plus a nightly encrypted logical dump to separate object storage. See [MIGRATION_STRATEGY.md §8](MIGRATION_STRATEGY.md). Deleted-account data leaves the backups once they rotate out. The privacy policy discloses this. |

## 13. Soft-delete policy

Soft delete (`deleted_at timestamptz NULL`) is used **only** where there is a recovery or sync requirement:

- **Syncable user rows**: tombstones for delta pull (the table list is in §8).
- **Journal entries** (`journal_entries`): soft-deleted for an undo window, then hard-deleted by `maintenance:purge`.
- **Moderated content:** `posts`, `comments` (hidden but retained for the moderation trail).
- **Custom deeds** (`deeds` with an owner): soft deleted so history still resolves the name.

Everything else is hard deleted. All unique constraints on soft-deletable tables are **partial** (`WHERE deleted_at IS NULL`).

## 14. Enum strategy

| Use **Postgres enums** when… | Use **lookup tables** when… |
|---|---|
| The set is fixed by code behavior and changes only with a code release | Admins can add or modify values, or the values carry translations or metadata |

**Postgres enums** (adding a value = migration `ALTER TYPE … ADD VALUE`, never removal): `verification_token_type`, `session_client`, `completion_status`, `journal_entry_type`, `goal_period`, `goal_status`, `salah_prayer`, `salah_status`, `fast_type`, `group_type`, `group_role`, `member_status`, `visibility`, `report_reason`, `report_status`, `moderation_action_type`, `content_status`, `notification_channel`, `ai_insight_type`, `ai_message_role`, `export_status`, `locale_code` (`en`,`bn`).

**Lookup tables:** `roles`, `permissions`, `deed_categories`, `life_balance_categories`, `sunnah_practices`, `dhikr_presets`, `achievements`, `islamic_content_sources`.
